## 1. Введение
Проект «КубКубыч» предназначен для работы с каталогом наборов, корзиной и заказами покупателей. Цель разработки — объединить публичный каталог и управление покупкой в одном веб-приложении.

Задачи проекта: описать предметные сущности; реализовать поиск и подборки; предоставить покупателю корзину и оформление; разделить права; обеспечить административное управление; организовать обработку отзывов и аналитическую выдачу.

## 2. Анализ аналогов
Публичная страница [LEGO Shop By](https://www.lego.com/en-us/categories/shop-by) предлагает выбор наборов по теме и возрасту. Эти способы отбора использованы при определении сущности Category и возрастных полей Product.

[Brickset Sets](https://brickset.com/sets) содержит каталог и средства поиска, списки тем и годов. Сравнение показывает важность идентификации наборов и структуры каталога. Внутренние таблицы и административные функции аналогов не исследовались.

Аналитический вывод: каталог следует строить вокруг серии и товара, а покупку — вокруг собственных транзакционных сущностей корзины и заказа.

## 3. Архитектура приложения
Серверная часть использует Django и Django REST Framework. Django отдаёт HTML-шаблоны, JavaScript запрашивает JSON через API и строит интерфейс. Серверный HTML CRUD товаров реализован отдельно через ModelForm.

~~~mermaid
flowchart TD
    B[Браузер] --> H[HTML-представления Django]
    B --> A[REST API]
    H --> T[Шаблоны]
    A --> P[Права и сериализаторы]
    P --> S[Бизнес-сервисы]
    S --> O[Django ORM]
    P --> O
    O --> D[База данных]
    S --> Q[Попытка постановки задач Celery]
~~~

Главная маршрутизация находится в kubkubych/urls.py, настройки — в kubkubych/settings.py. Приложения users, products, cart, orders, product_reviews, analytics и siteconfig разделяют ответственность по предметной области.

## 4. База данных
В локальной конфигурации применяется SQLite; настройками предусмотрено подключение PostgreSQL. Пользовательская модель User использует email как идентификатор входа.

Category хранит серии. Product содержит артикул, slug, характеристики, цену, скидку, остаток и файловые поля. CartItem и Favorite связывают пользователя с товаром. Order хранит заказ, OrderItem — снимок купленных позиций. Review содержит оценку и результаты модерации. SiteSetting хранит единые контакты и тексты.

~~~mermaid
erDiagram
    USER ||--o{ ORDER : owns
    USER ||--o{ CART_ITEM : selects
    USER ||--o{ FAVORITE : marks
    USER ||--o{ REVIEW : writes
    CATEGORY ||--o{ PRODUCT : contains
    PRODUCT ||--o{ ORDER_ITEM : purchased
    PRODUCT ||--o{ CART_ITEM : selected
    PRODUCT ||--o{ FAVORITE : marked
    PRODUCT ||--o{ REVIEW : rated
    ORDER ||--o{ ORDER_ITEM : contains
~~~

Уникальные ограничения защищают идентификаторы и пары связанных объектов от повторения. Денежные значения используют Decimal. OrderItem хранит название, артикул и цену на момент покупки, чтобы последующее изменение каталога не изменяло снимок заказа.

## 5. Административная часть
Django Admin доступен по /admin/. ProductAdmin содержит поиск, фильтры, readonly-временные метки, календарную навигацию и вычисленную цену. OrderAdmin отображает позиции через inline. ReviewAdmin предоставляет массовую модерацию.

Category и Product зарегистрированы через ImportExportModelAdmin. Исторические модели Product и Order подключены через HistoricalRecords. Специализированный SimpleHistoryAdmin пока не зарегистрирован; стандартная история Django не равнозначна просмотру исторических снимков библиотеки.

ReportLab используется PDF-действием списка товаров. Генератор записывает артикул, название, остаток и базовую цену; кириллический шрифт и перенос длинных строк отдельно не настроены.

## 6. Главная страница
IndexView возвращает index.html. На странице находятся популярная и скидочная подборки и поиск. Данные загружаются API, карточки формирует productCard из static/js/app.js.

ProductViewSet рассчитывает средний рейтинг, число отзывов, избранное и продажи. Популярная подборка сортируется по продажам и избранному; скидочная отбирается условием discount_percent__gt=0. ORM использует связанные Product, Category, Review, Favorite и OrderItem.

Числовые счётчики главной заданы шаблоном. Они не являются автоматически пересчитанной аналитикой базы.

## 7. Детальная страница
Адрес товара содержит slug. ProductDetailView передаёт его шаблону, JavaScript получает товар и рисует характеристики, цену и управляющие кнопки. Отзывы загружаются отдельно.

В текущей реализации HTML получает ProductListSerializer фильтрацией списка по slug. Поле description находится только в ProductDetailSerializer; поэтому описание не поступает на страницу этим запросом. В работе выявлено расхождение между ожидаемыми данными шаблона и фактической сериализацией.

HTML CRUD доступен под /manage/products/. Форма проверяет данные, нормализует артикул, принимает изображение и спецификацию. Редактирование использует instance, удаление — POST подтверждения. Защищённые ссылками заказов товары не могут удаляться свободно.

## 8. Авторизация и бизнес-правила
Интерфейс покупателя применяет JWT. api.js хранит токены в localStorage, добавляет Authorization и при 401 пытается обновить access token. Административные HTML-формы используют сессионную авторизацию.

Корзина принадлежит текущему пользователю. Перед добавлением проверяются активность товара и остаток. Оформление заказа выполняется create_order_from_cart в транзакции: проверяются позиции и сумма, создаётся снимок заказа, уменьшаются остатки, очищается корзина. Предел суммы — от 500 до 100 000 рублей.

Order.set_status ограничивает переходы между состояниями. Отмена возвращает остаток. Отзыв допускается после доставленного заказа; повторный отзыв на тот же товар запрещён уникальностью пары и проверкой. Правка покупателем повторно отправляет отзыв на модерацию.

Онлайн-оплата демонстрационная, реальный платёжный шлюз не подключён. Фоновая почта и периодические задачи требуют отдельно работающих Celery, Redis и почтового сервера.

## 9. Запуск и результаты проверки
Применённые пользователем команды:
~~~powershell
python manage.py showmigrations
python manage.py migrate
python manage.py seed_store
python manage.py runserver 127.0.0.1:8001
~~~

Предоставленный вывод migrate сообщил No migrations to apply. seed_store завершился результатом: 8 серий, 24 товара, 2 заказа, 5 отзывов. Проверка сервера сообщила System check identified no issues и запуск на http://127.0.0.1:8001/.

Это подтверждает запуск Django и подготовку данных, но не является результатом полного тестового набора или всех пользовательских сценариев. Полный suite ранее не получил итогового статуса; заявление о прохождении всех тестов не делается.

## 10. Заключение
Создано приложение с разделением интерфейса, API, моделей и бизнес-сервисов. Реализованы каталог, корзина, оформление, статусная модель, отзывы, аналитика и административные функции. Подтверждён локальный запуск и применение миграций.

Анализ выявил ограничения, значимые для демонстрации: сокращённая сериализация карточки, отсутствие собственных template tags/filters, специализированного просмотра истории и доказанного Excel-сценария, а также объём seed-данных меньше десяти в ряде таблиц. Эти ограничения не подменены утверждениями о завершённой реализации.
