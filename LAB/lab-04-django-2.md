### Цель и основание разбора

Разобрать условия лабораторной работы на реализации интернет-магазина «КубКубыч»: объяснить назначение каждого средства, показать место в коде и последовательность его работы.

Источник условий — раздел «Весна 2026» [курса СДО](https://online.mospolytech.ru/course/view.php?id=15327), перечень, ранее зафиксированный при разборе курса. Повторная сверка авторизованной страницы при подготовке этой редакции не выполнялась. Нумерация ниже служит для объяснения пунктов и не является дословным воспроизведением страницы.

Разбор выполнен по текущему исходному коду. Фрагменты сокращены до существенных строк; схемы — поясняющие иллюстрации с условными значениями, не скриншоты и не протокол браузерных тестов. Исходный код при подготовке отчёта не изменялся.

### Общая логика

Администратор открывает HTML-форму, отправляет поля и файлы, Django проверяет данные и сохраняет Product. После успешного действия браузер перенаправляется на список. Эти представления отделены от REST API.

## 1. ModelForm и HTML CRUD

### Что это

ModelForm создаёт форму на основе модели; CRUD — создание, чтение, изменение и удаление.

### Где находится

[products/site_views.py](../products/site_views.py) — product_create, product_update, product_delete.

### Основной код

~~~python
form = ProductForm(request.POST or None, request.FILES or None)
if request.method == 'POST' and form.is_valid():
    product = form.save(commit=True)
~~~

### Как работает

ProductForm объявлена в products/forms.py. Маршруты products/site_urls.py подключены под /manage/products/: список, create/, <int:pk>/edit/, <int:pk>/delete/. Создание сохраняет новый объект, редактирование передаёт instance существующего. GET удаления показывает подтверждение, POST удаляет. Декоратор admin_required требует сессионный вход и роль admin. PROTECT у позиций заказа может запретить удаление; отдельная обработка ProtectedError здесь отсутствует.

### Визуализация

~~~text
/manage/products/
  → create/ → новая форма
  → ID/edit/ → заполненная форма
  → ID/delete/ → подтверждение → POST
~~~

Состояние требования: CRUD реализован. Удаление товара, связанного с заказом, ограничено PROTECT; браузерный полный сценарий в этом отчёте не заявлен как проведённый тест.

## 3. Переопределение model.save

### Что это

Метод модели добавляет действия перед записью в базу.

### Где находится

[products/models.py](../products/models.py) — Product.save.

### Основной код

~~~python
def save(self, *args, **kwargs) -> None:
    if not self.slug:
        base = slugify(self.name, allow_unicode=True) or 'set'
        self.slug = f'{base}-{self.article}'.lower()
    super().save(*args, **kwargs)
~~~

### Как работает

При пустом slug он строится из названия и артикула, затем вызывается стандартное сохранение. Существующий slug не обновляется автоматически при смене названия. save не вызывает full_clean автоматически: проверки модели — отдельный механизм.

### Визуализация

~~~text
Пустой slug → сформировать → super().save
Заданный slug → сохранить без генерации
~~~

Состояние требования: Реализовано в коде.

## 6. Form.save(commit)

### Что это

commit управляет тем, записывать ли подготовленный объект сразу.

### Где находится

[products/forms.py](../products/forms.py) — ProductForm.save.

### Основной код

~~~python
def save(self, commit=True):
    product = super().save(commit=False)
    if commit:
        product.save()
        self.save_m2m()
    return product
~~~

### Как работает

Сначала создаётся или изменяется экземпляр без записи. commit=True вызывает сохранение модели; commit=False возвращает объект для дальнейшей обработки вызывающим кодом. save_m2m предусмотрен для связей формы, однако поле favorited_by_users не включено в Meta.fields: эта форма не редактирует избранное. internal_note — дополнительное поле формы, оно не сохраняется в модель.

### Визуализация

~~~text
Форма → объект в памяти
commit=True → база
commit=False → вызывающий код
~~~

Состояние требования: Реализовано в коде.

## 7. ManyToManyField с through

### Что это

Связь многие-ко-многим реализуется собственной промежуточной моделью.

### Где находится

[products/models.py](../products/models.py) — Product.favorited_by_users и Favorite.

### Основной код

~~~python
favorited_by_users = models.ManyToManyField(
    settings.AUTH_USER_MODEL,
    through='Favorite',
    related_name='favorite_products',
    blank=True,
    verbose_name='Добавили в избранное',
)
~~~

### Как работает

Пользователь может выбрать много товаров, товар — понравиться многим пользователям. Favorite хранит user, product и created_at. UniqueConstraint запрещает повтор одной пары. Записи создаются действием favorite в products/views.py, а не ProductForm.

### Визуализация

~~~text
Пользователь ← Favorite(user, product, дата) → Товар
~~~

Состояние требования: Реализовано в коде.

## 8. select_related

### Что это

Средство заранее загружает одиночные связанные объекты через SQL JOIN.

### Где находится

[products/site_views.py](../products/site_views.py) — product_manage_list.

### Основной код

~~~python
queryset = Product.objects.select_related('category').exclude(is_active=False).order_by('name')
~~~

### Как работает

category — ForeignKey. При обращении к серии товара Django использует данные той же выборки, вместо отдельной загрузки серии для каждой строки. Это подходит для одиночных связей, не для коллекции отзывов.

### Визуализация

~~~text
Запрос Product JOIN Category → товар + серия
~~~

Состояние требования: Реализовано в коде.

## 9. prefetch_related

### Что это

Средство загружает коллекции связей дополнительным запросом и связывает их в Python.

### Где находится

[products/views.py](../products/views.py) — ProductViewSet.get_queryset, ветка retrieve.

### Основной код

~~~python
queryset = queryset.prefetch_related(
    Prefetch(
        'reviews',
        queryset=Review.objects.filter(is_approved=True).select_related('author'),
        to_attr='approved_reviews',
    )
)
~~~

### Как работает

Для API retrieve заранее загружаются одобренные отзывы, внутри них — авторы. Результат доступен в approved_reviews. Это фрагмент ветки get_queryset; не каждая HTML-страница обязательно вызывает retrieve. Фактическое число SQL-запросов здесь не измерялось.

### Визуализация

~~~text
Запрос товаров + запрос отзывов с авторами → связанный результат
~~~

Состояние требования: Реализовано в коде.

### Где находится

~~~python
if settings.DEBUG and not getattr(settings, 'TESTING', False):
~~~

В kubkubych/settings.py условно подключены приложение и middleware, в requirements.txt указан пакет. Показ панели зависит от DEBUG, режима тестирования и INTERNAL_IPS. Наличие подключения не доказывает, что панель уже наблюдалась в браузере.

### Визуализация

~~~text
HTML-запрос в режиме разработки → панель → вкладка SQL
~~~

Состояние требования: Подключение есть; скриншот и измерение запросов не получены.

## Ответы на контрольные вопросы

### Что делает pip install?

pip устанавливает Python-пакет и его зависимости. Для проекта используется python -m pip install -r requirements.txt: запуск через выбранный интерпретатор снижает риск установки не в то окружение. Затем отдельно выполняются migrate и runserver.

## Результат и вывод

Показаны форма товара, HTML CRUD, обработка валидации, переопределения save, явная промежуточная связь и средства загрузки связанных объектов. Дополнительная заметка не сохраняется; избранное не редактируется этой формой. Проверка UI и измерение SQL остаются отдельными действиями.
